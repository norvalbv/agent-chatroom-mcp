## Reasoning

**Step 1 — What double value does `1e-7` actually hold?**

`1e-7` is not exactly representable in binary. Writing it as `m × 2^e` with `1 ≤ m < 2`:
`log2(1e-7) ≈ -23.2535`, so `e = -24` and `m = 1e-7 × 2^24 = 1.6777216` exactly (a terminating decimal).

The 52-bit stored fraction is `k = round(0.6777216 × 2^52)`. Computing exactly:
`0.6777216 × 2^52 = 3052186745220936.3419136` — the fractional part is `0.3419136 < 0.5`, so `k` rounds **down**. This means the stored double is **strictly less** than the true decimal value `1e-7` (not a tie, so no round-to-even ambiguity applies).

**Step 2 — How much less, exactly?**

Using exact integer arithmetic, the relative shortfall is
`delta = 3419136 / 2^76 = 4.525188817...×10⁻¹⁷` (an exact rational, computable to arbitrary precision).

So `value/1e-7 = 1 − delta = 0.99999999999999995474811183...` (16 nines, then `5474811183…`).

Normalizing: `value = 9.99999999999999995474811183...`×10⁻⁸ → i.e. **9.[15 nines]5474811183...×10⁻⁸**.

**Step 3 — Apply the `%.17g` rule.**

`P = 17`. Rounding to `P` significant digits means keeping the leading digit plus 16 more, then looking at digit 18 to decide rounding. Digit 18 (the first excluded digit) is **`4`**, which is less than 5 — so we round **down/truncate**, and critically, **there is no carry propagation**. The mantissa stays at `9.999...95` form; it never reaches `10.000...0` (which is what would be required to produce `1e-07` after normalization).

Since the true exponent is `X = -8` and `X ≥ -4` is false, the `g` rule mandates **e-style** output (not f-style), and since the rounded fractional digits end in a nonzero `5`, no trailing zeros exist to strip.

**Step 4 — Why A is wrong.**

`1e-07` could only be the correct `%.17g` output if rounding the exact double to 17 significant digits produced a carry all the way through (mantissa becoming exactly `1.0000000000000000`), which would require the double to be **greater than or equal to** `1e-7` at the relevant rounding boundary. We've shown via exact fraction arithmetic that the double is strictly **less than** `1e-7`, and the digit immediately beyond the 17-digit cutoff is `4` (not ≥5), so no such carry occurs. `"1e-07"` looks like the output of a "shortest round-trip representation" algorithm (what `1e-7` prints as by default in many languages), which is a different algorithm than "correctly round the exact binary value to exactly 17 significant digits" — the spec requires the latter.

Implementation B's output correctly reflects that the double is slightly below `1e-7` and reports it at full 17-significant-digit precision without collapsing it.

FINAL: B
