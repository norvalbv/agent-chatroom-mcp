# Proposed decision: verify-head-fail-to-pass

From the reuse survey (docs/reuse-survey-2026-09-23.md, sections "Verify gate" and "Reviewer and verifier prompts") and the open items todo/verify-gate-fail-to-pass.md and todo/reviewer-prompts-exercise-behaviour.md; built on branch reuse/review-quality. A human promotes this into docs/decisions/ with `guard-decisions add`; nothing is adopted automatically.

DECISION RECORD
- slug: verify-head-fail-to-pass
- context: The verify gate accepts a passing structured report of any command from a non-author, including a rerun of the author's own tests. In the census of all 260 structured verify heads recorded before 2026-09-23 (paper, "How seats check each other"; bench/results/verify-practice), 126 reported only builds, type checks or existing tests and 43 the scripted smoke client. In the review-act audit (bench/results/review-audit), rerunning the author's test, suite or build was the largest category, 154 of 331 acts, with the lowest defect-flagged share: 39/154, against 25/38 for a check the author had not supplied. Re-read under the rule below, 237 census heads parse with exit_code 0 and none of them records a failing-before run: 123 name no commit, and 114 name a commit but no base commit (scripts/verify-fail-to-pass-regression.ts). The 2026-09-23 owner decision on consensus-requires-scrutiny keeps the mandatory challenge "until verification uses checks the author cannot satisfy with their own evidence".
- ruling (stage 1; the hub still runs nothing):
  - The verify head gains `base_commit`, `base_exit_code`, `refactor` and `kind`. A head counts only when it satisfies every earlier rule and carries fail-to-pass evidence in SWE-bench's sense: it names the proposal's `commit` and the parent commit before the change (`base_commit`), the two differ, and the same check exited nonzero at `base_commit` (`base_exit_code`) and 0 at `commit` (`exit_code`). The rule is `failToPassShortfall` in src/hub.ts.
  - Refactor path: `"refactor":true` with `base_exit_code` 0 also counts. This is SWE-bench's PASS_TO_PASS: a change that alters no behaviour has nothing that can fail before it. A refactor claim whose check failed at `base_commit` is contradictory and is refused. Passing at both commits without `"refactor":true` is refused.
  - `kind` is optional and self-declared: `existing_tests`, `own_check` or `exercised`. These are the census classes in scripts/paper-verify-practice.ts: existing_tests is its existing_tests; own_check is its own_check; exercised covers its app_in_browser and agents_on_changed_build. The hub records `kind` but does not gate on it.
  - Every earlier rule is unchanged. The entry must come from a non-author on a different connection, name the exact proposal id and be newer than the current text. While the assigned reviewer is present, only that reviewer's entry counts; once they leave, any non-author's entry counts. `exit_code` must be 0. Executable challenges are unchanged: a plain rerun of the challenger's command still answers one, but it does not satisfy the gate without fail-to-pass evidence. `challengeRequired()` is unchanged.
  - One function, `verifyEntryVerdict`, decides both whether an entry counts and what the refusal says. The refusal quotes `VERIFY_HEAD_EXAMPLE` and `VERIFY_HEAD_RULE`. It also names up to the two latest entries that concern this proposal but do not count, with the reason for each (for example: no `base_commit`, `base_exit_code` 0 without `"refactor":true`, `"kind"` not one of the three, written before v2's text, or from a second name on the proposer's connection). A malformed head names the field to fix, through `readVerifyHead`, which parseVerifyHead now wraps.. It never names the author's own entry, another proposal's entry or a `.partial` entry.
  - A conclusion in a room that requires verification records `verification: {key, by, path, base_commit, commit, kind?}`. The CONSENSUS REACHED notice gets a line naming the reviewer and whether the conclusion passed as fail-to-pass or on the refactor path.
  - The same commit changes every place that teaches the head: prompts/loop.md, prompts/recruit.md, the verifier text in src/revive.ts, the join_room `require_verification` description, the board_set key description, the propose-time refusal ("someone else must then check it themselves", no longer "run it"), the reviewer-assignment notice, the bench-build runner prompt, scripts/smoke.ts and the repo skills/swarm/SKILL.md (done-means-independently-verified). prompts/minimal.md is not changed (minimal-prompt-hub-carries-coordination): flat seats learn the head from the tool description and the refusal.
  - The reviewer prompts (loop.md, recruit.md, verifier.md, the revive verifier text) take two rules from the OpenHands extensions qa-changes plugin (MIT). Do not only rerun the author's tests: exercise the changed behaviour the way its users would, and note that `--help` is not a check. Say what could not be verified and what was tried: switch approach after three failed attempts and stop after two approaches. If nothing was verified, write `verify/<area>.partial`, which never counts.
- consequences:
  - Positive: A passing rerun of the author's suite no longer satisfies the gate on its own. A reviewer now has to find or write a check that fails without the change, which is the SWE-bench FAIL_TO_PASS shape. A refactor-path pass is named on the conclusion rather than hidden. When an entry exists but does not count, the refusal names it and says why.
  - Negative, stage 1 is still self-reported: the hub resolves neither commit and runs nothing. A reviewer can type `"base_exit_code":1` without running anything. That makes a false head costlier to write, because it names two commits and a specific failure, but no less possible. This is why the mandatory challenge stays.
  - Negative, a trivial "fails before": a test file that does not exist at the parent commit fails there with file-not-found. SWE-bench avoids this by applying the test patch to the base. The prompts ask for the same check against the parent's code, but the hub cannot tell the difference.
  - Negative: The refactor path is the new loophole: any rerun can be relabelled `"refactor":true`. Stage 1 mitigates it only by making it visible, in the conclusion notice and `conclusion.verification.path`.
  - Negative: Commit names are free strings. Relative refs such as HEAD~1 are accepted, and non-git workspaces (the bench-build runner's `git init` workspace has no commits) must name something.
  - Negative, cost: the tool list grows by about 470 characters per seat per turn. While a proposal is unverified, its `blocked_by` refusal grows by about 340 characters (306 to 647 for a typical proposal id), plus up to two lines naming entries that do not count.
  - Negative: This is a breaking change for rooms already running. After a hub restart, an open proposal's head without fail-to-pass fields stops counting.
  - Negative, benchmarks: the bench-build runner's prompt text changes, so its runner_sha256 changes, and re-runs of arm C in bench-build or bench-rq1 on this hub are a new condition. Pools 2 and 3 are pinned to study/pool-throughput and are unaffected.
  - Negative, paper: paper/system.md and "What the gate asks for" in paper/sections/results.tex describe the gate at census time. parseVerifyHead still reproduces the census's schema_valid count, 241 of 260 row by row, so the paper's number stands.
- researched:
  - SWE-bench, Jimenez et al. 2023, arXiv:2310.06770: FAIL_TO_PASS and PASS_TO_PASS tests. Already in docs/research-index.md.
  - OpenHands extensions, qa-changes plugin, MIT, github.com/OpenHands/extensions, fetched at commit 76bbae25 (2026-09-23). From skills/qa-changes/SKILL.md: "Run the code, not the tests", the bug-fix before/after comparison, "Knowing When to Give Up" and the "Unable to Verify" report section. Also plugins/qa-changes/scripts/prompt.py ("Do NOT run the test suite", "Running `--help` ... is NOT functional verification") and plugins/qa-changes/README.md. NEW relative to the settled axes.
  - Own data: bench/results/verify-practice, bench/results/review-audit, docs/reuse-survey-2026-09-23.md and its skeptic check. The skeptic confirmed the qa-changes licence and quotes, and that the Claude Code code-review plugin's prompt is proprietary.
- evidence: A probe of the change itself, in its own required shape: the same script exits 1 against the hub at d755a873, where a passing rerun head counts, and exits 0 on this branch, where it does not and a fail-to-pass head does. On a private hub built from the branch, driven by scripted MCP clients over HTTP, a reviewer wrote seven non-counting heads, and each refusal named the entry and the field or step to fix. A non-reviewer's head and a head that predated an amend were each named back with the reason. A fail-to-pass head with every agree still waited for a challenge under auto. Each kind, no kind, and the refactor path each concluded, and each notice named its path. After a hub restart on the same data directory, `conclusion.verification` read back unchanged.
- rejected:
  - Having the hub resolve both commits with git (the survey's own stage 1): the hub's working directory is not necessarily the room's repository, seats work in other worktrees and other repositories, and bench-build workspaces have no commits. A check that fails open when it cannot resolve a commit adds little. This is left to its own change; it overlaps pool item h06 (docs/experiments/pool-throughput/pools/hub/pool.json), which is benchmark material.
  - Having the hub or a trusted runner execute the check at both commits (stage 2): it runs commands that seats supplied from the hub process. It needs a sandbox and its own decision, and it is the revisit condition of the consensus-requires-scrutiny owner decision.
  - Gating on `kind`, for example refusing existing_tests: kind is self-declared, and a regression test the author added that fails before the fix is exactly SWE-bench's FAIL_TO_PASS test. What the hub enforces is the fail-to-pass shape, not the label.
  - Declaring a refactor in the proposal text: that means parsing proposal prose, which done-means-independently-verified rejected as gameable.
  - Dropping the mandatory challenge now: the owner decision stands, and stage 1 is still self-reported.
  - Requiring the new fields inside parseVerifyHead: that would change what the census's schema_valid measures. The rule lives in failToPassShortfall and the parser only type-checks.
  - Copying the Claude Code code-review plugin's prompt text: its licence is proprietary.
- revisit-when:
  - A counted head claims a nonzero base_exit_code, and rerunning its command at base_commit passes. That is a fabricated fail-before, and stage 2 is due.
  - Refactor-path passes exceed a quarter of the verified conclusions in a run, read from `conclusion.verification.path`.
  - Rooms stall with only "does not count: no base_commit" refusals, because reviewers cannot produce a failing-before check.
  - Stage 2 lands. Then revisit the consensus-requires-scrutiny owner decision.
