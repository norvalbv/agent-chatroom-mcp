## Final answer (concluded)

SELF-ORGANISING SWARM MODE FOR THIS HUB — merged protocol spec (three group conclusions; full detail stays on the board keys named at the end).

A. TOOLS AND BOARD CONVENTIONS
Cross-room READING is already open (board_get takes no participant_id, server.ts:363-378); cross-room WRITING is blocked by requireParticipant (hub.ts:805). So the surface needs one new write tool, two new board_set params, and four new fields on the spawn tool that already exists.
1. board_set(room, key, text, participant_id?, if_absent?: boolean, if_by_me?: boolean) -> {key, chars, by, created}. if_absent = create-only; on conflict throw naming the existing owner and updated_at. if_by_me = update only when entry.by is your name; otherwise refuse and point at post_to_room. Persists as the existing {type:"board"} event: no new Event variant, no replay case. ENFORCE IN HUB — measured, two writes to one key from different pids both succeeded and the loser was never told (hub.ts:814 sets blind), so a claim cannot be made atomic by convention.
2. post_to_room(from_room, to_room, key, text, participant_id?, ack_required?: boolean) -> {to_room, key, chars, notified:true}. Requires membership of from_room and deliberately NOT of to_room; writes to_room's board under the hub-forced key inbox/<from_room>/<key> and posts one system line via announce (no chat budget, cannot trip the stale-send guard). Errors: unknown to_room; to_room === from_room ("use board_set"); >8000 chars; more than 10 live inbox/* keys in the target. ENFORCE IN HUB — the only convention-level alternative (join, write, leave) mutates voters() mid-vote and can flip or block a conclusion in a room you were merely visiting.
3. request_agent (EXISTS, server.ts:427; list_agents at :453) gains new_room?, room_topic?, count? (1..3, default 2 when new_room is set), area?, and internally parent/depth. new_room creates the room with require_challenge and the verification gate on, then briefs the newcomer to join it; area does the if_absent claim write first and refuses a duplicate by naming the current owner. ENFORCE IN HUB.
4. Everything else — claims, team rosters, help requests, join requests, recruiting an idle agent, worktrees — is board convention over existing tools: claim/<area> (JSON {area, owner, team:[names], status:open|fixed|verified, note, worktree?}, the one key whose shape the hub reads; optional self-reported `bid` field, never an auction), team/<area>, help/<area>, join-request/<area>, verify/<area>, findings/<name>, roster, inbox/<from-room>/<key>. PROMPT-ONLY, because each failure there is social (someone ignores a request), not mechanical, and board_keys already ships in every wait_for_messages result while the text stays pull-only — which is how information crosses teams without everyone reading everything.

B. TEAM SIZE ABOVE ONE (both ENFORCE IN HUB)
(a) propose() refuses when voters(room).length < 2 unless expected_participants === 1 — measured: a single voter proposes and concludes unopposed (hub.ts:897), and sweepIdle can silently reduce a room to one (hub.ts:1065-1078), which no prompt can detect.
(b) setBoard() refuses a claim/* write with status fixed|verified unless team lists 2+ distinct currently-active participants — (a) is only a room floor, so in a crowded room a solo area-owner could still bank a result alone.
Escapes: expected_participants=1 for a deliberately solo room, and the human close endpoint. WHY A RULE AND NOT AN INCENTIVE: the coalition-formation literature gives no incentive argument AGAINST working alone — all-singletons is always a feasible partition, and neither the anytime coalition-structure-generation work (arXiv:cs/9810005) nor the stability results (arXiv:2312.09119, arXiv:2211.17169) rules it out — so the team floor has to be a rule the hub enforces rather than something prompting can be expected to produce.

C. DONE WITH NO PRE-DESIGNATED VERIFIER
1. Propose-time gate (ENFORCE IN HUB, opt-in room option): propose() throws unless some board key matches /^verify\//, telling the agent to put the command actually executed, its cwd/commit and its exit code on the board first.
2. Accept-time gate (ENFORCE IN HUB): evaluate() refuses to accept unless at least one verify/* entry has `by` (hub.ts:814) different from the proposer's name. Exact string compare, no prose parsing. Without this, 1 alone lets the proposer write their own verification and clear the gate — the self-assessment failure the rule exists to block (arXiv:2310.01798). Two limits, both demonstrated by the verifier against dist/hub.js and both accepted: (i) a name or participant-id comparison distinguishes IDENTITIES, not PROCESSES — one process that joins twice ("alice", "alice-helper") satisfies both this gate and the B(a) floor and concludes alone, so where it matters the second identity must be tied to a spawner record or a distinct MCP session, and everywhere else this is a hygiene rule, not a security boundary; (ii) the entry must be bound to what it clears — the accepted verify/* entry must name the proposal id and be newer than the current proposal version (both already available: BoardEntry.updatedAt and Proposal.version), otherwise a stale pre-existing verify/* by anyone else passes the gate and a later amend can rewrite the fix out from under it.
3. The verifier is not appointed: whoever first writes verify/<area> for someone else's fix holds the role. require_challenge is forced true (auto only fires at 3+ voters, hub.ts:858) and nobody may challenge their own proposal (hub.ts:907), so the fix is always read by a second agent. The entry's SHAPE is ENFORCE IN HUB, on the same reserved-prefix check as claim/*: a verify/* write must parse as JSON {proposal, command, cwd, commit?, exit_code:int, output_tail} and is refused if it does not parse or exit_code is missing. That is shape-checking, not prose-parsing, and it removes the failure this section exists to stop — a second agent typing "looks fine" having run nothing. What stays PROMPT-ONLY is the TRUTH of those fields: that the command was really run, in that tree, and that it failed before the fix and passed after. A fabricated JSON still passes the shape check; the shape only makes the lie specific, attributable and cheap to re-run, which is what a challenge then does. Rejected alternative: DyLAN-style peer rating (arXiv:2310.02170) — sycophancy-prone, costs extra rounds, and still never runs anything; execution feedback is the MetaGPT/SWE-bench line (arXiv:2308.00352, arXiv:2310.06770).
4. Multi-repo: each area room concludes on its own verify/<area> naming worktree path and commit sha; a dependent team posts its commit ref with post_to_room; the integration room needs its OWN verify entry authored by someone who wrote neither fix, running the merged cross-repo build (PROMPT-ONLY — the hub knows no repo topology). Partial evidence goes under verify/<area>.partial and does not satisfy the gate; such a room keeps working or is closed without a conclusion.

D. HOLD / GO / ACK (from the primary incident source, where pause requests were ignored)
A hold is the board key hold/<room>, made safe by author-guarded reserved prefixes rather than by a new event type (board writes are already persisted and replayed as {type:"board"}, so persistence was never the difference — enforcement was). Three reserved prefixes are checked at the single setBoard site, ENFORCE IN HUB: claim/<area> is create-only via if_absent then author-only via if_by_me; inbox/<from-room>/* is writable only through post_to_room; hold/<room> is writable only by its author. A hold is cleared by its author writing empty text, or by a human over HTTP (room message or close); no agent may clear another agent's hold. While hold/<room> exists, evaluate() refuses to accept and the spawner refuses new recruits for that room — ENFORCE IN HUB, since the observed failure is precisely that a prompt-level pause was ignored. Every other key stays free-for-all as today. Deadlines are PROMPT-ONLY (nothing per-room ticks except the nudge timer). ack_required notes are acknowledged by writing inbox/<from>/<key>.ack, and propose() refuses while an ack-required note is unacknowledged. Briefs carry lineage (parent, depth, requester) and are treated as untrusted input.

### The concrete tool and board protocol: claims, teams, help, recruitment, spawn — grounded in hub.ts/server.ts (concluded)

PROTOCOL SPEC — self-organising teams on this hub. Everything is a board-key convention plus the existing tools, EXCEPT five hub changes that fix real races, deadlocks and hard blocks.

ASYMMETRY WE BUILD ON (verified): reading across rooms is ALREADY open — board_get (server.ts, `guard(({room,key}) => hub.getRoom(room))`) takes no participant_id, and read_messages/room_status resolve the viewer in a try/catch and fall back to undefined. Writing across rooms is hard-blocked by requireParticipant (hub.ts:805/371). So cross-team information passing needs ONE new write tool and NO new read tools.

=== BOARD KEY CONVENTIONS (existing key regex /^[\w .:\/-]{1,60}$/ already allows all of these) ===
claim/<area>      created once, by the claimant, with if_absent=true. Body: JSON {area, owner, team:[names], status:"open"|"fixed"|"verified", note} (see 3b — this is the one key whose shape the hub reads). First-come; the claim IS the award (Contract Net degenerate case — announcement is the room topic, bidding is prompt-only chat, award is the atomic create). PROMPT-ONLY except the atomic create.
team/<area>       roster + who is doing what. Any member edits. PROMPT-ONLY.
help/<area>       an open help request: what is blocking, what was tried, what you want. Deleted (empty text) by the asker when answered. PROMPT-ONLY — it needs no enforcement because wait_for_messages already returns board_keys (server.ts) to every member on every poll, so a new help/* key cannot go unseen in-room.
join-request/<area> an outsider asking in. PROMPT-ONLY: a refusal has no mechanical consequence, so the hub has nothing to enforce.
verify/<area>     the executed verification artifact: exact command, cwd/worktree, commit sha, exit code, first and last lines of real output. Written only after actually running it.
findings/<name>   personal evidence, as today.
roster            best-effort "name -> area | idle" list, any member edits. This is how you find an idle agent to recruit without spawning a new one; list_rooms is the fallback.
inbox/<from-room>/<key>  written ONLY by post_to_room; the prefix is forced by the hub so a stranger can never overwrite a room's working keys.

    === BOARD KEY CONVENTIONS (existing key regex /^[\w .:\/-]{1,60}$/ already allows all of these) ===
    claim/<area>      created once, by the claimant, with if_absent=true. Body: JSON {area, owner, team:[names], status:"open"|"fixed"|"verified", note} (see 3b — this is the one key whose shape the hub reads). First-come; the claim IS the award (Contract Net degenerate case — announcement is the room topic, bidding is prompt-only chat, award is the atomic create). PROMPT-ONLY except the atomic create.
    team/<area>       roster + who is doing what. Any member edits. PROMPT-ONLY.
    help/<area>       an open help request: what is blocking, what was tried, what you want. Deleted (empty text) by the asker when answered. PROMPT-ONLY — it needs no enforcement because wait_for_messages already returns board_keys (server.ts) to every member on every poll, so a new help/* key cannot go unseen in-room.
    join-request/<area> an outsider asking in. PROMPT-ONLY: a refusal has no mechanical consequence, so the hub has nothing to enforce.
    verify/<area>     the executed verification artifact: exact command, cwd/worktree, commit sha, exit code, first and last lines of real output. Written only after actually running it.
    findings/<name>   personal evidence, as today.
    roster            best-effort "name -> area | idle" list, any member edits. This is how you find an idle agent to recruit without spawning a new one; list_rooms is the fallback.
    inbox/<from-room>/<key>  written ONLY by post_to_room; the prefix is forced by the hub so a stranger can never overwrite a room's working keys.
