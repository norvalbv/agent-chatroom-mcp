\section{Evaluated system}
\label{sec:system}

The evaluated build of \texttt{agent-chatroom-mcp} gave each chatroom seat an independent opening before shared discussion. Seats could propose and amend one answer, challenge a quoted span, and vote on the current proposal. Agreement votes had to quote the proposal; the room used a supermajority rule that required unanimity with three active seats. A verification gate required a machine-parseable verdict from a connection other than the proposer, and the hub assigned that reviewer. The verify gate and reviewer assignment were present before both studies. Kick, replace and heartbeat changes dated 22 September were later additions and were not evaluated here. Study 1 chatroom cells record hub entry hash \texttt{66f9d135\ldots}; run artifacts carry the revision used for each cell. The design offers routes for correction, but this paper does not isolate any route's effect.


This distinction between a build's presence and its measured effect is central to the system description. The revision hash establishes which code the chatroom cells entered; it does not say which part of that code determined an answer. A later hub feature cannot be credited with an earlier result merely because it now appears in the repository. The outcome comparison is between complete arm protocols as recorded, with any finer process account left to the limited seat summaries.

Arm A used one agent on the same public task brief. Arm K ran fresh, non-communicating A-style attempts and selected one answer without access to the hidden oracle. For the two interpreter tasks, it chose the most frequent normalized final answer, breaking a tie by sub-seed. For printf, it ran candidate programs on a fixed public-specification probe set and chose the implementation with the greatest execution agreement. Arm B in Study 2 passed one builder's output to a reviewer for possible revision; AH used one agent at higher effort. Thus B was run, while Study 1 has no B cell.

All cost-per-correct figures use API list prices and include the attempts needed to produce the selected answer. They describe these accounts and dates. A chatroom conclusion, a vote, or a participant's reported confidence never served as the correctness oracle. This matters particularly for process evidence: the retained Study 1 room summaries can say that a correction happened, but cannot prove that a challenge, vote, or verification gate caused it.
